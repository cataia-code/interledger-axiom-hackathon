Resumen

API en Node.js 24 + Express 5 (JavaScript ESM), con PostgreSQL vía Drizzle y autenticación con Better Auth montada bajo /api/v1/auth.

Express 5Better Auth 1.7Drizzle ORM PostgreSQL 17node --test + supertestESLint

URL base local: http://localhost:3000/api/v1. Todas las respuestas son JSON.

Arranque local

cd api
cp .env.example .env     # ajusta BETTER_AUTH_SECRET (32+ caracteres aleatorios)
npm install
npm run db:up            # Postgres en Docker (puerto 5432)
npm run db:migrate       # crea las tablas
npm run dev              # servidor con recarga en :3000
npm test                 # pruebas (necesitan Postgres arriba)

Convenciones

Formato: peticiones con Content-Type: application/json.

Versionado: todo cuelga de /api/v1.

Errores propios (rutas inexistentes, fallos internos): { "error": { "message", "code" } }.

Errores de auth (los devuelve Better Auth): { "message", "code" }. Los dos formatos conviven por ahora.

Seguridad base: helmet (cabeceras seguras) y cors.

Usuario autenticado

GET/api/v1/me

Devuelve el usuario de la sesión. Requiere Authorization: Bearer <token>, con el token que devuelven el registro y el login (o la cabecera set-auth-token).

curl localhost:3000/api/v1/me -H 'Authorization: Bearer <token>'
200 {"user":{"id":"…","email":"ana@ejemplo.com","name":"Ana","role":"buyer","emailVerified":false}}
401 {"error":{"message":"Authentication required","code":"UNAUTHORIZED"}}

Está en /api/v1/me y no bajo /auth, porque /api/v1/auth/* lo atiende Better Auth.

Registro e inicio de sesión por rol /api/v1/auth/buyer/* · /api/v1/auth/seller/*

Comprador y vendedor tienen rutas separadas. Comparten tablas y sesiones, pero cada login solo acepta su rol. Un vendedor siempre tiene organización y sucursal: se crea junto con la cuenta. Las rutas genéricas de Better Auth para registrarse e iniciar sesión (/auth/sign-up/email, /auth/sign-in/email, /auth/sign-in/email-otp) están cerradas y responden 404 ENDPOINT_MOVED.

POST/api/v1/auth/buyer/sign-up

Crea una cuenta de comprador, inicia sesión (devuelve token) y envía un código de verificación al correo (la verificación es opcional).

POST/api/v1/auth/buyer/sign-in POST/api/v1/auth/seller/sign-in

Inicia sesión con correo y contraseña, solo si la cuenta tiene el rol de la ruta. No exige el correo verificado. El rol se comprueba después de validar la contraseña, para no revelar qué correos existen; si no coincide, la sesión recién creada se revoca y no se devuelve ningún token. El login de vendedor exige además que existan su organización y al menos una sucursal.

-d '{"email":"ana@ejemplo.com","password":"Password-12345"}'

200 {"token":"…","user":{"id":"…","email":"ana@ejemplo.com","name":"Ana","role":"buyer","emailVerified":false}}
401 {"error":{"message":"Invalid email or password","code":"INVALID_EMAIL_OR_PASSWORD"}}
403 {"error":{"message":"This account is a seller; use the seller login","code":"WRONG_ROLE"}}
403 {"error":{"message":"A seller must have a store","code":"STORE_REQUIRED"}}   (o ORGANIZATION_REQUIRED)
POST/api/v1/auth/buyer/sign-in/otp POST/api/v1/auth/seller/sign-in/otp

Inicia sesión con un código de un solo uso (antes hay que pedirlo con send-verification-otp). Mismas reglas de rol que el login con contraseña. No crea cuentas: un correo desconocido no puede registrarse con un código.

-d '{"email":"ana@ejemplo.com","otp":"123456"}'
200 {"token":"…","user":{"id":"…","email":"ana@ejemplo.com","name":"Ana","role":"buyer","emailVerified":false}}
400 {"message":"Invalid OTP","code":"INVALID_OTP"}   403 WRONG_ROLE

Rutas compartidas /api/v1/auth/* (Better Auth)

POST/api/v1/auth/email-otp/send-verification-otp

Envía (o reenvía) un código al correo. Un código nuevo invalida el anterior.

typePara qué
sign-inIniciar sesión con código
email-verificationReenviar el código de verificación

-d '{"email":"ana@ejemplo.com","type":"sign-in"}'
200 {"success":true}
POST/api/v1/auth/email-otp/verify-email

Verifica el correo con el código de 6 dígitos recibido.

-d '{"email":"ana@ejemplo.com","otp":"123456"}'
200 {"status":true,"token":null,"user":{…,"emailVerified":true}}
400 {"message":"Invalid OTP","code":"INVALID_OTP"}
POST/api/v1/auth/sign-out

Cierra la sesión y revoca el token (enviado en Authorization: Bearer, con cuerpo {}). Después, /me responde 401.

Better Auth expone más rutas bajo /api/v1/auth/* (por ejemplo cambio y restablecimiento de contraseña, get-session). Solo están documentadas arriba las que están probadas. Estas rutas devuelven errores como {"message","code"}, sin el envoltorio error.

Flujos de auth

A. Comprador

POST /auth/buyer/sign-up: se crea la cuenta (buyer), se inicia sesión (devuelve token) y se envía un código de verificación.
Opcional: POST /auth/email-otp/verify-email con el código marca el correo como verificado.
Más tarde: POST /auth/buyer/sign-in (contraseña) o send-verification-otp + POST /auth/buyer/sign-in/otp (código).

B. Vendedor

POST /auth/seller/sign-up con los datos de la cuenta y de la tienda: se crean usuario (seller) y tienda juntos, y se devuelve el token.
Más tarde: POST /auth/seller/sign-in o /auth/seller/sign-in/otp. Un comprador que intente entrar aquí recibe 403 WRONG_ROLE (y al revés).
Limitación conocida: como la verificación es opcional, un usuario que se registró con contraseña y no verificó su correo pierde la contraseña si luego entra con código (Better Auth la borra y revoca sus sesiones para evitar robo de cuentas). Después, el login con contraseña da 401 hasta restablecerla. Decisión tomada: no se limita el login con código a correos verificados, así que el comportamiento se acepta por ahora.

Rate limiting

Por IP, ventana de 60 s, activo en todos los entornos. Los contadores están en memoria (se reinician con el servidor). Si la API va detrás de un proxy, hay que configurar trust proxy en Express y las cabeceras de IP de confianza en Better Auth; si no, el límite puede falsearse o aplicarse a la IP del proxy.

Cómo añadir un endpoint propio

  1. Servicio en src/services/ con la lógica y el acceso a la base de datos.
  2. Controlador en src/controllers/: valida la entrada, llama al servicio y responde (los errores se lanzan como HttpError y los recoge errorHandler).
  3. Ruta en src/routes/index.js, con requireAuth y, si hace falta, requireRole('seller').
  4. Si hay tablas nuevas: archivo propio en src/db/, añadirlo a drizzle.config.js y a src/db/index.js, y luego npm run db:generate y npm run db:migrate.
  5. Prueba en test/ con supertest.

Modelo relacional

PostgreSQL, 6 tablas en dos grupos. Autenticación (azul) guarda quién es el usuario y cómo entra; Negocio (verde) guarda lo que hace un vendedor: su organization (datos legales; representa a un usuario seller) y las sucursales (store) de esa organización. Comprador y vendedor comparten user, y el campo role (buyer o seller, no nulo) los distingue.

PK clave primariaFK clave foráneaUK únicoNN no nuloLínea punteada: relación lógica, sin FK
RelaciónCardinalidadDetalle
user → session1 a Nsession.user_id, cascada. Un usuario puede tener varias sesiones (varios dispositivos). El token es único.
user → account1 a Naccount.user_id, cascada. Una fila por método de acceso; con contraseña, provider_id = credential y password guarda el hash.
user → organization1 a 0..1organization.user_id, único y cascada. Todo seller tiene exactamente una organización (se crea en su registro); un buyer no tiene ninguna. Esa regla la aplica la API, no la base de datos.
organization → store1 a Nstore.organization_id, cascada. Una organización tiene una o más sucursales (la primera se crea en el registro; el resto con POST /stores). El nombre de la sucursal es único dentro de su organización.
verificationsin FKCódigos de un solo uso. identifier tiene la forma tipo-otp-correo (por ejemplo sign-in-otp-ana@ejemplo.com) y value guarda el hash del código.

Decisiones de diseño

  • Roles: uno por usuario (buyer | seller), fijado por la ruta de registro; el cliente no puede enviarlo (input: false). Un vendedor siempre tiene organización y sucursal. Un correo no puede ser comprador y vendedor a la vez.
  • Login separado por rol: mismas tablas y sesiones, rutas distintas; cada login rechaza (403) las cuentas del otro rol y no deja sesión viva.
  • Sin registro por código: las cuentas solo nacen en /auth/buyer/sign-up y /auth/seller/sign-up.
  • Sesión móvil: token de sesión opaco y revocable de Better Auth, no JWT con refresh.
  • Envío de correo sin await: evita diferencias de tiempo que revelen si un correo existe.
