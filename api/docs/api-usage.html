Resumen

API en Node.js 24 + Express 5 (JavaScript ESM), con PostgreSQL vía Drizzle y autenticación con Better Auth montada bajo /api/v1/auth.

Express 5Better Auth 1.7Drizzle ORM PostgreSQL 17node --test + supertestESLint

URL base local: http://localhost:3000/api/v1. Todas las respuestas son JSON.

Convenciones

Formato: peticiones con Content-Type: application/json.

Versionado: todo cuelga de /api/v1.

Errores propios (rutas inexistentes, fallos internos): { "error": { "message", "code" } }.

Errores de auth (los devuelve Better Auth): { "message", "code" }. Los dos formatos conviven por ahora.

Seguridad base: helmet (cabeceras seguras) y cors.

Usuario autenticado

GET/api/v1/me

Devuelve el usuario de la sesión. Requiere Authorization: Bearer <token>, con el token que devuelven el registro y el login (o la cabecera set-auth-token).

curl localhost:3000/api/v1/me -H 'Authorization: Bearer <token>'
200 {"user":{"id":"…","email":"ana@ejemplo.com","name":"Ana","role":"buyer","emailVerified":false}}
401 {"error":{"message":"Authentication required","code":"UNAUTHORIZED"}}

Está en /api/v1/me y no bajo /auth, porque /api/v1/auth/* lo atiende Better Auth.

Autenticación /api/v1/auth

POST/api/v1/auth/sign-up/email

Crea la cuenta con contraseña, inicia sesión (devuelve token) y envía un código de verificación al correo. La verificación es opcional. El rol siempre es buyer; un role enviado en el cuerpo se ignora.

  -H 'Content-Type: application/json' \
  -d '{"email":"ana@ejemplo.com","password":"Password-12345","name":"Ana"}'

422 {"message":"User already exists. Use another email.","code":"USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL"}
400 {"message":"Password too short","code":"PASSWORD_TOO_SHORT"}

Registrar un correo que ya existe responde 422.

POST/api/v1/auth/email-otp/verify-email

Verifica el correo con el código de 6 dígitos recibido.

-d '{"email":"ana@ejemplo.com","otp":"123456"}'

200 {"status":true,"token":null,"user":{…,"emailVerified":true}}
400 {"message":"Invalid OTP","code":"INVALID_OTP"}
POST/api/v1/auth/sign-in/email

Inicia sesión con correo y contraseña. No exige el correo verificado.

-d '{"email":"ana@ejemplo.com","password":"Password-12345"}'

200 {"redirect":false,"token":"…","user":{…}}
401 {"message":"Invalid email or password","code":"INVALID_EMAIL_OR_PASSWORD"}
POST/api/v1/auth/email-otp/send-verification-otp

Envía (o reenvía) un código al correo. Un código nuevo invalida el anterior.

typePara qué
sign-inIniciar sesión con código
email-verificationReenviar el código de verificación
forget-passwordReservado para recuperar contraseña (sin probar)
-d '{"email":"ana@ejemplo.com","type":"sign-in"}'
200 {"success":true}
POST/api/v1/auth/sign-in/email-otp

Inicia sesión con el código recibido. Si el correo no existe, crea el usuario ya verificado (con name vacío).

-d '{"email":"ana@ejemplo.com","otp":"123456"}'
200 {"token":"…","user":{…,"emailVerified":true,"role":"buyer"}}
POST/api/v1/auth/sign-out

Cierra la sesión y revoca el token (enviado en Authorization: Bearer, con cuerpo {}). Después, /me responde 401.

Devuelve la sesión actual o null. Todavía no acepta el token en Authorization: Bearer: eso llega en la fase 3.

Better Auth expone más rutas bajo /api/v1/auth/* (por ejemplo cambio y restablecimiento de contraseña, sign-out). Solo están documentadas arriba las que están probadas.

Flujos de auth

A. Registro con contraseña

POST /sign-up/email: se crea el usuario (buyer), se inicia sesión (devuelve token) y se envía un código de verificación.
Opcional: POST /email-otp/verify-email con el código marca el correo como verificado.
Más tarde: POST /sign-in/email devuelve token y user, verificado o no.

B. Login con código (sin contraseña)

POST /email-otp/send-verification-otp con type: "sign-in".
POST /sign-in/email-otp con el código: devuelve token y user.
Limitación conocida: como la verificación es opcional, un usuario que se registró con contraseña y no verificó su correo pierde la contraseña si luego entra con código (Better Auth la borra y revoca sus sesiones para evitar robo de cuentas). Después, el login con contraseña da 401 hasta restablecerla. Comprobado con el código actual. Pendiente de decidir: exigir verificar antes de permitir el login con código, o aceptar este comportamiento.

Decisiones de diseño

  • Roles: uno por usuario (buyer | seller). Nace buyer; pasará a seller al crear una tienda (fase 5). El cliente no puede elegirlo (input: false).
  • Sesión móvil: token de sesión opaco y revocable de Better Auth, no JWT con refresh.
  • Envío de correo sin await: evita diferencias de tiempo que revelen si un correo existe.
