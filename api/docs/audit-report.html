Axiom API: informe de auditoría

Auditoría de la API REST (rama feature/base_api_nodejs): pruebas automáticas, auditoría de caja negra contra el servidor real, rendimiento, concurrencia e integridad de datos. La auditoría no modificó código; después se corrigieron los hallazgos (ver Correcciones).

Resumen

Funcionalmente la API está correcta: ninguna regla de negocio falló y no hubo ningún error 5xx durante la auditoría. Se encontró 1 problema grave de robustez (la API se caía si Postgres cortaba una conexión) y 4 de severidad media o baja. Los 5 están corregidos y verificados (71 pruebas automáticas, ahora con 6 nuevas).

Hallazgos

Descripción original de cada hallazgo. Todos están corregidos.

Grave Corregido 1. La API se cae si Postgres cierra una conexión

Reproducido: al terminar las conexiones inactivas desde la base, el proceso Node termina. Falta un manejador pool.on('error', …) en src/db/index.js. Ocurriría con un reinicio de Postgres, un failover o un corte de red.

Corrección: registrar el evento error del pool (3 líneas) y registrar el fallo en el log.

Media Corregido 2. Solo el login tiene rate limit

Checkout, pagos, subida de imágenes y el webhook no limitan peticiones. La subida de imágenes (procesa con sharp) es el vector más costoso. Además el contador está en memoria: se reinicia con el servidor y no sirve con varias instancias.

Corrección: límites por ruta con express-rate-limit y, en producción, un almacén compartido (Redis).

Media Corregido 3. CORS abierto por defecto

access-control-allow-origin: * mientras CORS_ORIGIN no esté definido. Es la única comprobación de caja negra que falló.

Corrección: definir CORS_ORIGIN en producción y fallar al arrancar si falta.

Media Corregido 4. Faltan índices para ordenar por precio y buscar texto

Con 100 000 ítems el orden por precio tarda ~65 ms y la búsqueda 110–246 ms (recorre toda la tabla). Con unos miles de ítems no se nota.

Corrección: índice parcial sobre (price_amount, id) para ítems activos y un índice pg_trgm (GIN) sobre nombre y descripción.

Baja Corregido 5. Detrás de un proxy no se ve la IP real

Falta trust proxy en Express y la configuración de IP de Better Auth: el rate limit contaría la IP del balanceador.

Observaciones

  • npm audit: 4 avisos moderados, todos en drizzle-kit/esbuild (herramientas de desarrollo; no afectan al servidor en ejecución).
  • Las rutas compartidas de Better Auth (/auth/email-otp/*, /auth/sign-out) usan otro formato de error que el resto (RF-TRA-04, ya conocido).
  • Resend nunca se probó con una API key real; el transport de correo tiene la cobertura más baja (75 %).

Alcance y límites

  • Medido en una máquina local con Postgres en Docker; las cifras de rendimiento no equivalen a producción. No se hicieron pruebas de carga sostenidas ni de estrés prolongado.
  • La auditoría de caja negra usó una instancia en modo test (límite de login 1000). El límite real de 5 por minuto se comprobó aparte contra el servidor de desarrollo.
  • El cierre de conexiones de Postgres (hallazgo 1) se probó en una instancia aparte.
  • No se probó el envío de correo con Resend ni un proveedor de pago real (el actual es un placeholder).
